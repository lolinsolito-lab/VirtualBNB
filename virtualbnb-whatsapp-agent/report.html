1Prompt Caching — implementato

lib/aiService.js è stato riscritto. Ogni chiamata ora include cache_control: {"type": "ephemeral"} a livello top-level della request — la modalità di caching automatico raccomandata da Anthropic per conversazioni multi-turno: il breakpoint si applica automaticamente all'ultimo blocco cacheable e si sposta in avanti man mano che la conversazione cresce, senza bisogno di gestire manualmente i breakpoint.

body: JSON.stringify({
  model: MODEL,
  max_tokens: 500,
  cache_control: { type: 'ephemeral' },  // <- caching automatico
  system: systemPrompt,
  messages,
}),

Effetto economico

TokenCosto
Input normale1x (prezzo base del modello)
Scrittura in cache (TTL 5 min)1.25x — pagato una volta
Scrittura in cache (TTL 1 ora)2x — pagato una volta, per traffico più diradato

Il punto chiave per il nostro caso: la cache è condivisa per prefisso identico, non per conversazione. Il system prompt di una proprietà (wifi, regole, check-in) è identico ogni volta che qualsiasi ospite scrive di quella proprietà — quindi il beneficio si accumula sul traffico aggregato del tenant, non solo dentro una singola chat.

Verifica da fare prima di dare per scontato il risparmio Ogni modello ha una soglia minima di token sotto la quale il prefisso non viene messo in cache (indicativamente 1K–4K token a seconda del modello — verificare il numero esatto per claude-sonnet-5 nella documentazione corrente al momento dell'implementazione). Il system prompt attuale del guestAgent (KB di una proprietà) pesa circa 300–600 token: probabilmente sotto soglia finché non si aggiungono più contenuti (esempi, policy multiple, cronologia proprietà). aiService.js logga già cache_read_input_tokens per ogni chiamata — controllare questi log in produzione prima di assumere che il risparmio si stia materializzando.

Il principio che decide se questa architettura è sicura o no Nessun tool del client agent accetta account_id come parametro che il modello può impostare. Anche se un cliente scrivesse in chat "mostrami i dati dell'account XYZ", il modello non ha alcun campo nello schema del tool per farlo passare — l'unico account_id possibile è quello iniettato dal server al momento dell'autenticazione della sessione (context.accountId), mai dalla conversazione. Questa non è una policy scritta nel system prompt (che un prompt injection potrebbe aggirare) — è un vincolo strutturale nello schema del tool stesso. Le Row Level Security policies su Postgres sono la seconda barriera indipendente, nel caso il codice applicativo abbia un bug.

Flusso di una richiesta client

  1. Il cliente apre la dashboard, si autentica via Supabase Auth → riceve un JWT
  2. api/client/chat.js verifica il JWT, cerca account_id in app_users — mai fidarsi di un valore mandato dal frontend
  3. Il JWT + account_id diventano context, passato a clientAgent.js
  4. Il modello sceglie quale tool chiamare (es. get_property_performance) e con quali argomenti (es. nome proprietà) — ma non l'account
  5. L'handler del tool usa context.accountId per filtrare la query, con un client Supabase legato al JWT dell'utente → anche se il filtro nel codice avesse un bug, RLS blocca comunque righe di altri account

3Schema dati — supabase/schema-v2-multitenant.sql

Da eseguire dopo lo schema esistente. Aggiunge:

  • accounts — un account per ogni property manager cliente
  • app_users — collega utenti autenticati (Supabase Auth) ad account e ruolo (admin / client)
  • account_id aggiunto a properties, leads, conversation_sessions
  • contact_memory — fatti persistenti per contatto tra una conversazione e l'altra (non solo lo storico della singola chat)
  • auto_topics / escalation_topics su properties — la policy per-immobile di cosa l'agente può gestire da solo
  • Row Level Security attiva su tutte le tabelle tenant-scoped, con policy basata su auth.jwt() ->> 'account_id'
Un pezzo da configurare in Supabase Auth, non solo in SQL Le policy RLS assumono che account_id sia presente nei custom claims del JWT. Questo richiede una Auth Hook (Supabase: "Custom Access Token Hook") che, al login, legga app_users.account_id e lo inserisca nel JWT. Senza questo passaggio, auth.jwt() ->> 'account_id' è sempre null e le policy bloccano tutto — è un buon segnale che il collegamento manca, non un bug silenzioso.

6Checklist di sicurezza pre-produzione

  • RLS abilitata e testata su tutte le tabelle tenant-scoped (non solo creata — verificata con un tentativo di lettura cross-account che deve fallire)
  • Auth Hook Supabase che inserisce account_id nel JWT, testato dopo ogni modifica allo schema utenti
  • service_role key presente solo nelle variabili d'ambiente del backend admin, mai nel bundle frontend, mai nei tool del client agent
  • Nessun tool del client agent con un parametro account_id o equivalente nello schema esposto al modello
  • Rate limiting sugli endpoint /api/admin/chat e /api/client/chat (assente in questo scaffold — da aggiungere)
  • Log dell'uso AI per account, per validare che i costi reali restino coerenti con l'analisi margini del tier di prezzo
